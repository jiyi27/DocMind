# DocMind SQLite Concurrency Optimizations

## 决策背景 (Background)

在 DocMind 项目的早期版本中，我们为每次 API 请求或后端查询都使用 `aiosqlite.connect()` 建立一个全新的数据库连接。

这种模式在低并发和数据量较小的情况下可以正常工作，但在具有高并发读写请求的 Web 应用场景下（例如用户在浏览知识库的同时，后台异步任务正在向数据库写入大量文档块的元数据），SQLite 会遇到严重的性能和并发瓶颈，极易触发 `database is locked` 异常。

因此，我们对后端 SQLite 数据库的管理方式进行了重构，引入了以下两项核心优化：

1. **全局连接复用 (Global Connection Pooling)**
2. **开启预写日志模式 (Write-Ahead Logging / WAL)**

---

## 优化详解 (Details)

### 1. 为什么弃用“每次请求新建连接”？

`aiosqlite` 的底层实现机制是为每个独立的连接在后台开启一个**真实的操作系统线程**，以此来防止 SQLite 阻塞主线程的 AsyncIO 事件循环。

如果每个请求都执行一次 `connect()`：
- **资源浪费**: 频繁地创建和销毁线程会导致极高的 CPU 上下文切换和内存开销。
- **锁争抢加剧**: 多个不同的连接（线程）会像多个独立进程一样去激烈争抢 SQLite 数据库文件的“读写锁”。

**解决方案**:
在应用启动阶段 (`lifespan.py`)，我们初始化一个全局唯一的 `aiosqlite.Connection`，并通过 `get_db()` 依赖注入将其复用给所有的 HTTP 路由和后台任务。这样能极大减少线程开销并集中管理连接状态。

### 2. 为什么要开启 WAL 模式？

默认情况下，SQLite 使用传统的回滚日志 (Rollback Journal, `journal_mode=delete`) 模式。在这种模式下：
- **读写互斥**: 当一个连接正在**写入**时，会申请排他锁 (Exclusive Lock)，此时其他连接**既不能读也不能写**。
- **写写互斥**: 当多个连接同时准备**写入**时，只有一个能拿到预留锁 (Reserved Lock)，其他等待超时的连接就会直接抛出 `database is locked`。

这在频繁并发查询的 Web 应用中是致命的。

**开启 WAL (Write-Ahead Logging) 带来的改变**:
通过执行 `PRAGMA journal_mode = WAL;`，SQLite 的工作方式发生质变：
- **数据追加写入**: 所有的修改不再直接覆盖原始 `.db` 文件，而是被追加写入到一个全新的 `.db-wal` 预写日志文件中。
- **读写不再互相阻塞**:
  - 请求 A 可以在向 `.db-wal` 写入新数据的同时...
  - 请求 B 可以安全、无阻塞地从 `.db` (和已提交的日志) 中读取旧数据。
- 只有并发的“写-写”操作才需要短暂排队，极大幅度地降低了锁冲突的概率和时间。

> 配套设置: 我们同时将 `synchronous` 级别从 `FULL` (默认) 降到了 `NORMAL` (`PRAGMA synchronous = NORMAL;`)。这在 WAL 模式下是绝对安全且官方推荐的，可以减少磁盘的 `fsync()` 调用频率，进一步提升约 1-2 倍的写入吞吐量。

---

## 为什么 SQLite 官方不默认开启 WAL？

虽然 WAL 在 Web 服务/服务器端场景下优势明显，但 SQLite 作为一个极其通用的嵌入式数据库，默认没有开启它，主要基于以下兼容性考虑：

1. **破坏了单文件属性**: WAL 模式会额外产生 `.db-wal` 和 `.db-shm` (共享内存索引) 文件。如果用户只是简单地通过复制 `.db` 文件来备份或分享数据库，可能会丢失 `.db-wal` 中尚未同步的数据。
2. **网络文件系统 (NFS) 兼容差**: WAL 极度依赖底层文件系统对共享内存 (Shared Memory) 和严格文件锁的支持。在很多网络共享磁盘 (如 NFS、SMB) 上，这种支持可能存在缺陷，容易导致数据库损坏。
3. **只读介质受限**: 如果数据库部署在只读目录 (如 CD-ROM)，即便只是执行 `SELECT` 查询，WAL 也需要尝试创建或修改 `.db-shm` 文件，这会导致操作失败。

对于 DocMind 这样的后端服务程序：
- 数据库位于本地磁盘或 Docker 卷。
- 我们需要支撑 FastAPI 提供的高并发请求。
- 我们并不打算通过“复制粘贴单个 `.db` 文件”的方式来做热备份。

因此，**主动在初始化时开启 WAL 模式，是本项目必然且最佳的架构选择。**
